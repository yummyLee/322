# 开发原则

> **项目**：openworldtest  
> **引擎**：Godot 4.x  
> **最后更新**：2026-05-05  
> **适用范围**：所有系统、场景、脚本的设计与实现

---

## 一、组件即功能

> Scene 定义结构，Script 定义行为。挂上什么脚本，就是什么功能。

### 规则

- `.tscn` 场景文件只做**结构组装**：放 Sprite、CollisionShape、AnimationPlayer 等视觉/物理节点，不做业务逻辑
- 业务逻辑封装在**可复用的脚本组件**中，通过 `add_child()` 或在编辑器中挂载到节点
- 一个节点的功能 = 它身上挂的所有脚本组件的**并集**
- 移除一个脚本组件，该功能就消失，不影响节点其他行为

### 反例

```gdscript
# ❌ 把业务逻辑写在场景根节点的脚本里
# forest_monster.tscn → ForestMonster.gd
# 包含了移动、战斗、掉落、AI 全部逻辑
```

### 正例

```gdscript
# ✅ 逻辑拆分到独立组件，按需挂载
# forest_monster.tscn
#   ├── CombatantComponent   → 属性 + HP + 受击
#   ├── ChaseController      → AI 追击行为
#   ├── SpriteFrameMeleeHitbox → 帧窗近战判定
#   └── AnimatedSprite2D     → 表现
```

### 判断标准

问自己：**"如果我删掉这个脚本，节点还能正常工作吗（只是少了这个功能）？"**  
如果不能，说明耦合太紧，需要拆分。

## 二、数据驱动

> 数值和配置属于 Resource 文件，不属于代码。

### 规则

- 物品属性、怪物数值、技能参数、掉落表等 → `Resource` 子类或 JSON
- 代码中不硬编码具体数值（如 `damage = 50`），只写计算逻辑
- 新增内容 = 新增 `.tres` / 新增 JSON 条目，不改代码

### 正例

```gdscript
# ✅ 数值来自 Resource
var weapon: WeaponData = load("res://weapons/iron_sword.tres")
var damage := weapon.base_damage  # 来自数据，不是代码
```

### 反例

```gdscript
# ❌ 数值写死在代码里
var damage := 50.0  # 铁剑伤害
```

## 三、信号解耦

> 组件之间通过信号通信，不直接调用对方的方法。

### 规则

- 组件 A 需要通知组件 B 时，A 发射信号，B（或中间层）连接该信号
- 组件不持有对兄弟节点或父节点的强引用（避免 `get_parent().get_node("../X").do_something()`）
- 跨系统通信优先走 Autoload（事件总线模式）

### 正例

```gdscript
# ✅ CombatantComponent 用信号通知外部
signal died
signal health_changed(current_hp, max_hp)
# EnemyBase 连接信号即可，CombatantComponent 不知道谁在听
```

## 四、单一职责

> 一个脚本只做一件事，做好那一件事。

### 规则

- 脚本文件超过 200 行时，问自己"这个脚本在做几件事？"
- 每个 `class_name` 的职责能用一句话描述清楚
- 不相关的职责分到不同组件

### 示例

| 组件 | 职责 |
|------|------|
| `CombatantComponent` | 属性 + HP + 受击，不涉及移动和表现 |
| `ChaseController` | 追击移动 AI，不涉及战斗和属性 |
| `BuffRuntime` | Buff 计时与到期，不涉及具体效果实现 |
| `DamageCalculator` | 纯函数伤害计算，无状态，不依赖任何节点 |

## 五、Resource 优先

> 能用 Resource 定义的，不用代码定义。

### 规则

- 武器、防具、怪物、技能、Buff、任务、掉落表 → 全部定义为 Resource
- Resource 之间可以相互引用（如 WeaponData 引用 AttackPattern）
- Resource 可以在编辑器中可视化编辑，策划友好

### 优先级

```
Resource (.tres) > JSON > 代码常量 > 硬编码
```

---

## 六、最小侵入

> 新功能复用现有架构，不推翻重来。

### 规则

- 新增系统时，首先检查现有组件能否直接满足需求
- 需要新能力时，扩展现有组件而不是创建替代品
- 新旧代码走同一套数据管道（如所有属性修改都走 `CharacterAttributes.add_modifier()`）

---

## 七、测试可隔离

> 核心逻辑不依赖场景树也能运行。

### 规则

- 伤害计算、属性公式、Buff 逻辑等使用 `RefCounted`，在单元测试中直接 `new()`
- 需要场景节点的测试，创建最小 `.tscn` 或代码构造节点
- 提交前运行已有测试确保不回归

---

## 八、编辑器友好

> 策划和设计师不需要打开脚本编辑器就能调整游戏数据。

### 规则

- 所有可调参数通过 `@export` 暴露到 Godot 检查器
- Resource 字段加清晰的 `@export_group` 分组和 tooltip
- JSON 文件格式保持稳定，结构变更时同步更新文档
