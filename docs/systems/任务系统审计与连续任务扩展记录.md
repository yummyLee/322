# 任务系统审计与连续任务扩展记录

> 审计日期：2026-08-04  
> 首个正式接入任务：M1-00【窑火】

## 结论

现有 QuestManager 的“定义与实例分离、全局事件推进、跨场景常驻、存档序列化”方向合理，可以继续扩展，不需要推翻。但实现仍是扁平目标任务，不等同于旧设计文档中规划的完整阶段系统。

本次已补齐连续主线最容易出错的基础能力：

- 任务唯一 ID 冲突时拒绝覆盖并报错。
- 同一任务处于进行中或已完成状态时拒绝重复接取。
- `prerequisites` 在接取时强制校验。
- `auto_accept_when_unlocked` 支持前置任务交付后自动串联下一任务。
- `design_code / chapter_id / sequence` 分离策划编号、章节与排序信息。
- 加载全部任务定义后检查空目标 ID、重复目标 ID、自身前置和不存在的前置。
- 任务进度、完成记录与剧情触发 flag 均进入现有存档。

## 当前能力边界

目前一个 QuestDef 只有一组并行目标，适合 M1-00 这类单阶段任务。以下需求应在出现第二个复杂主线前实现为正式 StageDef，而不应继续堆叠剧情脚本分支：

- 一个任务内连续发生三段以上目标与场景状态变化。
- 可选目标、ALL/ANY/SEQUENCE 完成模式。
- 任务失败、超时、暂停和重试。
- 分支汇合、互斥任务与阵营锁定。
- 动态生成的可重复委托实例。
- 任务版本迁移（已发布存档遇到目标改名或删除）。

## ID 约定

运行时 ID 一旦进入存档不得重命名：

```text
main_01_000_kiln_breakfast
│    │   │   └─ 稳定英文语义名
│    │   └──── 章内三位顺序
│    └──────── 两位章节号
└───────────── main / side / repeatable / hidden
```

策划文档使用短编号 `M1-00`。运行时逻辑只引用完整 ID，避免不同章节出现同名任务。

## 触发职责

- QuestManager：任务能否接取、目标进度、完成与存档。
- StoryState：一次性剧情镜头是否播过。
- 场景 QuestFlow 组件：把场景人物、演出与任务 API 编排起来。
- NPC：只提供稳定 `npc_id` 和交互入口，不自行保存任务状态。

这种分工可防止“区域触发一次、NPC 又接一次、读档再接一次”的重复问题。
