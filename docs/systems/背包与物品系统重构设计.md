## 一、设计目标

1. **常见排序**：名称、获取时间（新↔旧）、单价、堆叠总价、类型、稀有度、重量（若后续启用负重）等，与主流 ARPG / MMO 习惯一致。
2. **类型筛选**：按 `ItemData.ItemType`（及可选子类）过滤显示或弱化非匹配项；不改变「真实槽位」语义时须明确交互规则。
3. **背包扩展**：消耗类道具或任务奖励增加槽位；与存档、UI 网格行数解耦。
4. **物品实例信息**：在**不污染** `ItemData` 静态资源的前提下，为每格堆叠增加可选字段（如 `acquired_at`）。
5. **低耦合**：排序/合并策略集中在可单测的 `RefCounted` 或纯静态工具；`Inventory` 只负责槽位与变更信号；UI 只订阅视图状态。

## 二、参考游戏与交互惯例（简表）

| 来源习惯 | 可借鉴点 |
|----------|----------|
| **魔兽世界** | 分类 Tab / 筛选；「整理背包」一键重排；银行与背包分容器 |
| **暗黑类** | 稀有度色标已具备；「按类型聚类」+ 空位后置；筛选常配合仓库页签 |
| **JRPG** | 排序下拉框 + 升序/降序切换；获得顺序对图鉴/任务友好 |
| **生存建造** | 按价值排序便于卖店；按重量排序便于超载前整理 |

**本项目取舍**：先做 **一键排序 + 筛选 + 存档兼容**，不做过度复杂的「多页虚拟背包」除非容量显著增大。

## 三、核心数据模型：槽位字典规范（Slot Entry）

在现有 `item` + `quantity` (+ `durability`) 上扩展为**约定键名**（文档即契约，后续可抽 `InventorySlotEntry` 类封装读写，避免魔法字符串散落）：

| 键 | 类型 | 必填 | 说明 |
|----|------|:----:|------|
| `item` | `ItemData` | 是 | 静态定义引用 |
| `quantity` | `int` | 是 | ≥1 |
| `durability` | `int` | 否 | 仅 `max_durability > 0` 时有意义；缺省视为满 |
| `acquired_at` | `int` | 否 | **Unix 毫秒时间戳**（`Time.get_unix_time_from_system()` ×1000 取整）；用于「按获取时间排序」；缺省加载旧档时填 **0** 表示未知 |
| `instance_seed` | `int` | 否 | 预留：随机词条、鉴定前 ID 等（本期可不实现） |

### 3.1 堆叠合并规则（与 `acquired_at` 的关系）

- **无耐久**且 `max_stack > 1`：现有逻辑合并同 `id`。合并时 `acquired_at` 建议取 **`min(a, b)`**（保留「最早获得」时间，符合多数玩家对「获得顺序」的心理模型）。
- **有耐久**：保持现有行为 — **不自动合并**，避免耐久丢失；排序仍可按类型/名称等排列。

### 3.2 新增堆叠时写入时间

在 `Inventory.add_item` / `set_slot_direct` 创建新格时：若未传入 `acquired_at`，则设为当前时间戳。商人买入、奖励发放、合成产出等统一走 `Inventory` 或薄封装 `InventoryTransaction`（见下文），避免漏写。

## 四、排序与整理：公共模块抽取（减少重复）

### 4.1 现状

`StorageInventory._sort_inventory` / `_merge_stacks` / `_cmp_type_rarity_name` 已与玩家 `Inventory` 需求高度重合。

### 4.2 目标结构（建议）

新建 **`scripts/core/items/inventory_layout_ops.gd`**（`class_name InventoryLayoutOps`，`extends RefCounted` 或 `@static_unbound` 风格静态函数组）：

- `sort_slots(inv: Inventory, mode: SortMode, options: Dictionary = {}) -> void`  
  - 从 `Inventory` 读出非空槽 → 排序 → 写回连续槽位，尾部清空。  
  - `options` 可含 `ascending: bool`、`secondary: SortMode` 等扩展位。
- `merge_compatible_stacks(slots: Array) -> Array`  
  - 与现有 `_merge_stacks` 等价，但读写字典键名走统一常量（或 `InventorySlotEntry`）。
- `compare_slots_for_sort(a: Dictionary, b: Dictionary, mode: SortMode) -> bool`  
  - 供自定义排序与单测使用。

`StorageInventory.sort_tab` 改为 **委托** `InventoryLayoutOps.sort_slots`，删除重复实现。

玩家侧：`Inventory` 可增加薄封装 `func sort_inventory(mode: SortMode) -> void`，内部调用 `InventoryLayoutOps`，并保证对每个改写槽 `inventory_changed.emit(i)`（或新增 `inventory_rebuilt` 一次信号，二选一文档定死，避免 UI 漏刷）。

### 4.3 排序维度枚举（建议与 UI 对齐）

| 枚举值 | 主键 | 默认次序 | 备注 |
|--------|------|----------|------|
| `BY_NAME` | `item_name`（或 `id`） | 升序 A→Z | 中文环境可考虑 Collate；首版可用简单字典序 |
| `BY_ACQUIRED` | `acquired_at` | 降序（新在上） | 0 未知统一放最后或最前，需在 UI 说明 |
| `BY_VALUE_UNIT` | `value_gold` | 降序 | 单价 |
| `BY_VALUE_STACK` | `value_gold * quantity` | 降序 | 堆叠总价 |
| `BY_TYPE` | `item_type` → `item_sub_type` → `rarity` → `name` | 与现 `StorageInventory` 一致 | |
| `BY_RARITY` | `rarity` | 降序（高稀有在上） | |
| `BY_QUANTITY` | `quantity` | 降序 | |
| `COMPACT` | 先合并可合并堆叠，再 `BY_TYPE` | — | 与现逻辑对齐 |

**与拖拽的关系**：排序会改变槽位索引；玩家手动摆放会被覆盖 —— 与主流「整理」一致。若未来需要「锁定格」，可另加 `pinned: bool`（本期不做）。

## 五、筛选：表现层策略（避免双份数据源）

### 5.1 推荐方案 A（首版，实现成本低）

- UI 增加 `OptionButton` / `ItemType` 多选 chips：**全部 / 武器 / 防具 / 材料 / 工具 / 其他**。
- **不改变** `Inventory` 内顺序；`InventorySlotUI.refresh()` 根据当前筛选状态设置：
  - `modulate` 降低透明度，或
  - 边框变灰 + 可选 `mouse_filter` 在筛选非命中时禁止拖拽（避免误拖）  
- Tooltip 仍显示完整信息。

### 5.2 备选方案 B（体验更好，成本略高）

筛选开启时，将**命中物品紧凑排到前部**（实质是一次「按筛选键排序」+ 子排序），需与「手动排序」期望权衡；建议 **仅当用户点「整理」时** 与排序合并执行，避免打开筛选就改顺序。

**结论**：首版采用 **方案 A**；在文档与 UI 文案中写清「筛选仅高亮，不改变顺序」。

## 六、背包扩展

### 6.1 数据

- `Player` 或独立组件 `PlayerInventoryCapacity`（`Node` 子节点或 `RefCounted` 由 Player 持有）维护：
  - `base_slots: int`（默认 10，可来自常量或 `PlayerData` Resource）
  - `bonus_slots: int`（来自道具/成就）
  - `max_slots()` → `base_slots + bonus_slots`，上限防刷（如 120）

### 6.2 与 `Inventory` 的衔接

- 升级容量：`inventory.resize_slots(player.max_slots())`  
- **缩小**时现有逻辑会丢尾部物品 —— 扩展道具应 **只增不减**；若剧情需要收回容量，需单独设计「邮件返还」等，本期可禁止 `bonus_slots` 减少。

### 6.3 消耗「背包扩展符」

- **数据驱动**：`item_catalog.json` 增加字段，例如 `use_effect: "extend_inventory"`、`use_effect_args: { "slots": 4 }`（具体键名与 `ItemDatabase` 解析一致即可）。
- **执行路径**：`Player.try_use_consumable(item_id)` 或统一 `ItemUseRegistry`（Autoload 或静态表）根据 `use_effect` 分派；成功后 `bonus_slots += n` 并移除消耗品。
- **存档**：在 `PlayerRuntimeState.build_player_save_section` 增加 `inventory_bonus_slots`（或并入 `progression` 子字典，二选一，**一次定稿避免双写**）。

### 6.4 UI

- `InventoryUI` 构建网格时以 `get_slot_count()` 为准动态建格；或初始建最大格隐藏超出（不推荐）；推荐 **resize 后重建槽位控件** 并重新 `connect` 信号。

## 七、存档与兼容

### 7.1 序列化扩展

`PlayerRuntimeState._serialize_inventory` 每条在现有字段上可选增加：

```json
{ "item_id": "stone", "quantity": 12, "durability": -1, "acquired_at": 1715731200000 }
```

- 旧档无 `acquired_at`：反序列化填 **0**；排序时「未知时间」统一规则（建议永远排在**最后**，不论升序降序）。

### 7.2 储物箱

`StorageInventory.serialize` / `deserialize` 同步增加 `acquired_at` 读写，避免箱内与背包规则分裂。

## 八、模块边界与依赖图（文字版）

```
ItemData (Resource, 静态)
    ↑ 引用
Inventory (槽位数组 + add/remove/move + signal)
    ↑ 操作
InventoryLayoutOps (排序/合并/比较，无 UI)
    ↑ 调用
StorageInventory / Player / 商人逻辑
    ↑ 只读槽位 + 触发刷新
InventoryUI / InventorySlotUI (筛选表现、下拉排序、拖拽)
    ↑ 序列化
PlayerRuntimeState / SaveManager
```

**禁止**：`Inventory` 直接 `get_node` 找 UI；UI 不直接改 JSON 存档。

**可选薄层**：`InventoryTransaction`（`RefCounted`）封装「添加 N 个物品并统一打时间戳、合并失败回滚」— 仅当多处调用拾取/奖励时重复代码明显再抽。

## 九、UI 草图（逻辑布局）

在 `InventoryUI` 标题栏右侧或状态栏上方增加一行控件：

- `OptionButton`：排序方式（名称 / 获得时间 / 单价 / 堆叠总价 / 类型 / 稀有度 / 数量）
- `CheckButton` 或第二个 `OptionButton`：升序 / 降序
- `Button`：**整理**（执行 `COMPACT` 或当前排序 + 合并）
- `OptionButton`：**筛选**（全部 / 各 `ItemType`）

交互：

- 点「整理」→ 调用 `InventoryLayoutOps` → 全槽刷新。
- 仅切换排序键不自动重排：可二选一 —— **推荐**：切换排序键后**不**自动排序，须点「整理」或「应用排序」减少误操作；或提供设置项。

## 十、物品系统微调（不改静态表语义）

- **不**把 `acquired_at` 放进 `ItemData`：它是**实例**数据，属于槽位字典。
- `ItemData` 若需「图鉴首次获得时间」，属 **PlayerRuntimeState** 或 `CollectionBook` 独立字典（`item_id -> first_acquired_at`），与背包槽位解耦；本期可只做槽位时间，图鉴后续再接。

## 十二、风险与待定决策

1. **中文名称排序**：简单字符串序可能与玩家预期不符；可后续换 `String.compare` 的文化相关排序。
2. **筛选 + 拖拽**：若禁止非命中格拖拽，需明确「拖到装备栏是否仍允许」— 建议筛选下仍允许拖到装备槽（命中检测用真实物品）。
3. **时间戳来源**：单机用系统 Unix 时间即可；若担心改系统时间作弊，可改为「单调递增 `run_tick`」仅用于排序相对顺序（与真实时间脱钩）— 策划取舍。
